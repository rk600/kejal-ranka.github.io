ETL Architecture Modernization

Monolithic → Modular • 14+ pipelines • Months → Weeks onboarding

Problem

The entire analytics architecture was built on monolithic SQL pipelines with repeated code across multiple jobs. The same business logic (entity selection, savings calculation, metric computation) was copy-pasted into 14+ places. Adding a new operational stream required editing multiple jobs with high risk of mismatch. You couldn't answer basic questions like "what's the attribution breakdown by channel?" or "which segment drives our savings?" because the pipeline wasn't built for granularity.

Before vs After

Before (Monolithic)

  • Same logic duplicated across 14+ jobs
  • New stream onboarding: 2-3 months
  • Bug fix required editing multiple jobs
  • No granular attribution possible
  • High mismatch risk between outputs
  • Handover to new engineers: weeks

After (Modular)

  • Single source of truth per concern
  • New stream onboarding: 1-2 weeks
  • Fix once, propagates everywhere
  • Channel × segment × geography attribution
  • Guaranteed consistency across all outputs
  • Handover to new engineers: days

Architecture

MODULAR PIPELINE FRAMEWORK Module 1: Entity Attributes (single source of truth) └── Eliminates 3x duplication of entity metadata Module 2: Intervention Tracking (case-level) └── Standardized metadata at intervention_id level Module 3: Impact Calculation (modular per stream) └── Pluggable: each stream defines its own impact formula └── Shifted calculation earlier by 1-3 weeks (action date vs resolution date) Module 4: Selection Logic (configurable per program) └── Common scoring + program-specific filters Outputs (all consume from modules): ├── Executive Dashboard (reads Module 1 + 3) ├── Operational Reporting (reads Module 2 + 3) ├── Targeting System (reads Module 4) └── New Stream X (plug into Module 2 + 3 + 4 → done)

Key Design Decisions

Separation of Concerns

Each module owns exactly one domain: entity attributes, intervention metadata, impact calculation, or selection logic. No module knows about the others' internals. This means a change to how we calculate savings never accidentally breaks entity selection.

Pluggable Stream Architecture

New operational streams (like compliance checks or inventory programs) plug into the framework by defining their impact formula and selection criteria — without touching shared modules. This reduced onboarding from months to weeks.

Granular Attribution

By shifting savings calculation to the action date (instead of resolution date) and maintaining channel metadata, we enabled breakdowns by: outreach channel (email vs call), entity segment (domestic vs international), geography — all previously impossible.

Stakeholder feedback: "A healthy sustainable way to build our architecture" — Senior Manager. The modular design was recognized as a foundational improvement enabling the team to scale from 4 streams to 8+ without proportional engineering effort.

Impact

  • Onboarding: New streams launched in weeks instead of months
  • Consistency: Eliminated mismatch risk between outputs — single source of truth
  • Attribution: Enabled granular analysis (channel × segment × geography) previously impossible
  • Maintainability: Bug fixes and improvements propagate automatically
  • Knowledge transfer: New engineers productive in days, not weeks

Lessons Learned

  • Migration is harder than greenfield: We ran old and new pipelines in parallel for 4 weeks, comparing outputs row-by-row to ensure perfect parity before cutover.
  • Modules need contracts: Without clear input/output schemas per module, downstream consumers break silently. We defined explicit interfaces.
  • Sell the outcome, not the refactor: "Modular pipelines" doesn't excite stakeholders. "You can answer 'what channel drives our savings?' tomorrow" does.
