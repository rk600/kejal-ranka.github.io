Building a Self-Improving NLP Classification Pipeline

How I went from 18,000 unreadable text records to a system that classifies them automatically — and gets better on its own.

The Problem Nobody Could Solve Manually

Account managers across a major e-commerce marketplace record 18,000+ customer feedback entries per year. Each one contains signal: what programs customers care about, what's blocking their growth, and whether sentiment is shifting.

But it's all free text. Messy, inconsistent, multilingual. No one can read 18,000 entries. PMs were making strategy decisions based on gut feel and the 50 most recent entries they happened to skim.

The question: Can we turn this unstructured noise into structured intelligence — automatically, daily, without a team of labelers?

Why This Was Hard

This wasn't a simple "throw it at GPT" problem:

  • Domain complexity: 15 program categories that sound similar to outsiders (e.g., "serial number tracking for fraud detection" vs "investigating missing inventory during receiving" — both relate to inventory, but are completely different programs)
  • Multi-label: A single entry can discuss 3+ programs with different sentiments for each
  • No training data: Zero labeled examples existed when I started
  • Taxonomy mismatch: 38 different tag variants mapped to 15 canonical categories — with no documentation
  • Accuracy bar: PMs would lose trust if classifications were obviously wrong. One bad week = adoption dies.

The Architecture I Designed

DATA FLOW (fully automated, daily) 1. ETL (~4 min) SQL extracts 19K rows from source tables Joins seller metadata (revenue band, category, contact history) Deduplicates → parquet → S3 2. TRIGGER (event-driven) S3 PUT event → Lambda function ├── Dedup check: same file hash? → skip └── Cooldown check: ran in last 6 hours? → skip If conditions pass → start SageMaker job 3. ENRICH (~60 min, 25 concurrent threads) For each record: ├── Parse tags → canonical categories (38 variants → 15) ├── Retrieve Knowledge Base context (35 domain entries) ├── Embed text (1024-dim vector) ├── Find top-3 similar gold examples (cosine + boosting) ├── Build 6-layer prompt → LLM inference └── Post-process: normalize, match taxonomy, threshold 4. SERVE Enriched parquet (35 columns) → Dashboard PMs see: trends by category, sentiment shifts, top blockers

The Key Insight: 6-Layer Prompting

Zero-shot accuracy was ~70%. Not terrible, but not trustworthy. The breakthrough was layering context in order of specificity:

Layer 1: Stream identifier (which program family)
Layer 2: Knowledge base — what each program actually does, common mistakes to avoid
Layer 3: Taxonomy — predefined category labels to choose from (66 for one stream, free-form for another)
Layer 4: Few-shot examples — top-3 most similar validated entries from gold set
Layer 5: Blocker categories (10 predefined reasons for hesitation)
Layer 6: The actual text + output schema

This gives the model domain expertise, corrective examples, AND structured output constraints — all before seeing the input. Each layer addresses a specific failure mode I observed in earlier iterations.

Making It Self-Improving

The system gets better without human intervention through a three-phase learning mechanism:

Phase 1: Few-Shot RAG (live)

A gold set of validated examples is embedded as 1024-dim vectors. At runtime, each new record is embedded and compared via cosine similarity — with boosting (+0.1 for same stream, +0.15 for same category). Top-3 matches above threshold become in-context examples.

Phase 2: Auto-Harvest (live)

After each run, outputs with confidence ≥ 0.95 that match predefined taxonomy are automatically added to the gold set. This grew it from 10 manual examples to 222 — covering all 15 categories — without any human labeling.

Phase 3: Fine-Tuning (future)

At 2,000+ gold examples, export as training data and fine-tune a custom model. Target: 92%+ accuracy at lower per-call cost.

What I'd Do Differently

  • Start with the knowledge base, not the model. I spent 2 weeks tuning prompts before realizing the model simply didn't know what the programs were. The KB (35 curated entries) gave a bigger accuracy lift than any prompt engineering.
  • Build the evaluation harness first. I couldn't measure improvements reliably until I built the A/B eval script. Should have done this day 1.
  • Human-in-the-loop is a people problem, not a tech problem. The infrastructure for feedback is wired end-to-end (DynamoDB table, dashboard thumbs up/down). But no PM has bandwidth to review. The auto-harvest workaround sidesteps this for now.

Tech Stack

  • Compute: SageMaker Processing Jobs (ml.m5.xlarge), Lambda (Python 3.12)
  • AI: Claude 3 Sonnet (Bedrock), Titan Embeddings v2 (1024-dim)
  • Storage: S3 (parquet), DynamoDB (feedback loop)
  • Orchestration: Event-driven (S3 PUT → Lambda → SageMaker)
  • Monitoring: run_metrics.json (6 accuracy metrics tracked per run)
