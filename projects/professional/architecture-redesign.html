Killing a Monolith Without Breaking Production

How I convinced the team to let me rip apart 14+ working pipelines — and migrated without a single broken Monday dashboard.

← Back to portfolio

🎯 Situation

I inherited 14+ ETL pipelines built over 2 years by 3 different engineers. They all worked. They all ran on schedule. They all produced numbers that appeared in executive dashboards every Monday.

So what was the problem?

The same business logic — entity selection, savings calculation, metric computation — was copy-pasted across all of them. The savings formula existed in 4 different versions. The entity attributes query was duplicated 3 times with subtle differences. Nobody knew which version was "correct."

The real cost wasn't technical debt. It was unanswerable questions. "What channel drives our savings — email or phone?" Impossible to tell. "How do domestic vs international entities differ?" Can't say. The architecture wasn't built for granularity — it was built for "get a number out by Monday."

⚡ Task

Redesign the data architecture to:

  • Eliminate code duplication (single source of truth per domain)
  • Enable granular attribution (channel × segment × geography)
  • Make onboarding new operational streams fast (weeks, not months)
  • Do it without breaking a single Monday dashboard.

The Migration (Zero Downtime)

Week 1-2
Built new modular pipelines alongside the old ones. Both running in parallel. Leadership sees no change.
Week 3
Row-by-row output comparison: old vs new. Found 3 discrepancies — all bugs in the OLD code that nobody had noticed.
Week 4
Switched consumers to new modules. Old pipelines still running (safety net) but outputs disabled.
Week 5
Decommissioned old pipelines. Clean cutover after 1 week of verified parallel run.
Unexpected win: The parallel comparison revealed savings were being calculated from resolution date instead of action date — delaying attribution by 1-3 weeks. The "migration" was actually a correctness fix disguised as a refactor. Nobody would have found this without the row-by-row comparison.

📊 Result

Before

  • New stream: 2-3 months
  • Bug fix: edit N pipelines, pray
  • Attribution: impossible
  • Handover: weeks of context
  • "Why is this different?" → archaeology

After

  • New stream: 1-2 weeks
  • Bug fix: edit once, done
  • Attribution: channel × segment × geo
  • Handover: self-documenting
  • "Why is this different?" → impossible

🧠 What I Learned

  • Sell the outcome, not the refactor. "I want to modularize our pipelines" gets a polite no. "I can tell you whether email or phone drives more savings — but only if we restructure" gets a yes.
  • Parallel runs buy credibility. Those 2 weeks of comparison caught bugs that would have been blamed on "the migration broke something."
  • Perfect parity with broken code isn't a virtue. When comparison showed discrepancies, my instinct was to match the old output exactly. Investigating revealed the old code was wrong. Don't replicate bugs.
  • Modules need contracts. Without explicit input/output schemas, downstream consumers break silently. The hour spent defining interfaces saved weeks.
