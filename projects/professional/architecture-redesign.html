From Monolith to Modules: Redesigning a Data Architecture

Why I convinced the team to let me rip apart 14+ working pipelines — and how we migrated without breaking anything.

The Inheritance

When I joined the team, I inherited 14+ ETL pipelines built over 2 years by 3 different engineers. They all worked. They all ran on schedule. They all produced correct numbers.

So what was the problem?

The same business logic — entity selection, savings calculation, metric computation — was copy-pasted across all of them. The "entity attributes" query existed in 3 different pipelines with subtle variations. The savings formula was implemented 4 different ways. Nobody knew which version was "correct."

The real cost wasn't technical debt. It was that we couldn't answer questions the business needed answered. "What channel drives our savings — email or phone?" Impossible. "How do domestic vs international entities respond differently?" Can't tell. The architecture wasn't built for granularity.

Why "Just Add a Column" Wasn't the Answer

The instinct was: add channel attribution to the existing savings pipeline. But that would mean:

  • Adding it to 4 different implementations of the savings formula
  • Hoping all 4 produce the same answer (they wouldn't — they never did)
  • Next quarter, someone needs geography attribution → repeat across all 4 again

The root cause wasn't a missing column. It was an architecture that made every new requirement O(n) effort where n = number of pipelines containing that logic.

The Redesign

BEFORE: Monolithic (each pipeline owns everything) Pipeline A: [Select entities] → [Calculate savings] → [Compute metrics] → Output A Pipeline B: [Select entities] → [Calculate savings] → [Compute metrics] → Output B Pipeline C: [Select entities] → [Calculate savings] → [Compute metrics] → Output C (same logic, copy-pasted, subtly different) ───────────────────────────────────────────────────────── AFTER: Modular (separation of concerns) Module 1: Entity Attributes ← single source of truth Module 2: Intervention Tracking ← case-level metadata Module 3: Impact Calculation ← pluggable per stream Module 4: Selection Logic ← configurable filters Consumers: Dashboard → reads Module 1 + 3 Reporting → reads Module 2 + 3 Targeting → reads Module 4 New Stream → plugs into Module 2 + 3 + 4 (done in days)

The Hard Part: Migration Without Downtime

The pipelines ran daily. Leadership reviewed dashboards every Monday. I couldn't break anything during migration.

The approach:

  • Week 1-2: Built new modular pipelines alongside the old ones. Both ran in parallel.
  • Week 3: Row-by-row comparison — old output vs new output. Found 3 discrepancies (all bugs in the OLD code that nobody had noticed).
  • Week 4: Switched consumers to new modules. Kept old pipelines running but disabled their outputs.
  • Week 5: Decommissioned old pipelines after 1 week of clean parallel run.
Unexpected win: The parallel comparison found 3 bugs in the original pipelines — savings were being calculated from resolution date instead of action date, delaying attribution by 1-3 weeks. The "migration" was actually a correctness fix disguised as a refactor.

Before vs After

Before

  • New stream onboarding: 2-3 months
  • Bug fix: edit N pipelines, hope for consistency
  • Attribution: impossible (no channel/segment data)
  • Handover to new engineer: weeks of context
  • Answering "why is this number different?": archaeology

After

  • New stream onboarding: 1-2 weeks
  • Bug fix: edit once, propagates everywhere
  • Attribution: channel × segment × geography
  • Handover: self-documenting modules
  • "Why is this different?": impossible — one source

What I Learned

1. Sell the outcome, not the refactor

"I want to modularize our pipelines" gets a polite no. "I can tell you whether email or phone drives more savings — but only if we restructure the data layer" gets a yes. Always tie technical work to a business question someone is waiting to answer.

2. Parallel runs are non-negotiable

I was tempted to just swap in the new code. But the parallel comparison caught bugs that would have been blamed on "the migration broke something." Those 2 weeks of parallel runs bought credibility.

3. Perfect parity is the wrong goal

When the comparison showed 3 discrepancies, my instinct was "make the new code match the old exactly." But investigating them revealed the OLD code was wrong. Parity with a broken system isn't a virtue.

4. Modules need contracts

Without explicit input/output schemas per module, downstream consumers break silently when you add a column or change a type. I defined interfaces — the extra hour upfront saved weeks of debugging later.
